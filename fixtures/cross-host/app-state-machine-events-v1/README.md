# App state-machine ordered-event conformance (`runtime.wasm`)

Cross-host evidence for Spec 139 (embedder app state machine) and Spec 140 FR-013/FR-014:
the same app `state_machine` and the same command/terminal sequence must produce the same
ordered runtime events on every published embedder.

- `fixture.json`: the `init_header` (an app manifest `state_machine`) and the scenarios.
- `golden.json`: the ordered, id-normalized transcript the real `runtime.wasm` produces.
  Generated by the Rust reference, never hand-edited.

Scope: the permission and host-connector flow (`request_permission` then `capture_audio`,
with timeout, cancel, denied, duplicate, late-deadline, undeclared-terminal, and rejected
paths), plus one `analyze` scenario (`analyze_after_capture`, Decision 99) proving
`input_from: host_connector_result.artifact_base64` reaches the capability-invoke path. The
bundled fixture carries no capability artifact, so that scenario's nested execution fails
closed identically on every host (`capability_invoked` still fires, proving resolution
succeeded, before it fails); a scenario with a real capability artifact and
`capability_succeeded` is tracked separately, alongside the example apps in `#1503`.

## How a host runs it

For each scenario, on a fresh runtime:

1. Initialize `runtime.wasm` with a payload of a 4-byte little-endian header length, the
   `init_header` JSON, and an empty artifact.
2. Run each step in order:
   - `submit`: submit an `app_command` `{kind, command, payload, session_id?}`. `session` is
     `null` (new session) or a `$S<n>` placeholder for a session the runtime already assigned.
   - `complete`: submit a `host_connector_result` `{command_id, session_id, result_class,
     payload}` for a wait the runtime staged. `command` is a `$C<n>` placeholder, or omitted
     for the most recent wait.
   - `fire_deadline`: submit a `deadline_fired` `{command_id, session_id}` (same targeting).
3. After each step record the guest status code, the submit response, and drain every event.
4. Normalize runtime-assigned ids to `$S<n>` / `$C<n>` by first appearance (any
   `session_id` / `command_id` string), then compare each step to `golden.json`.

A rejected submit returns guest status `-1` with the response still written, so a host
bridge client must not swallow it: `guest_status` and the `rejected` response are part of
the contract.

Events are the raw runtime shape `{type, session_id, data}`. A host that maps them to a
public event type must keep the same order and content.

## Reference and regeneration

`crates/traverse-runtime/tests/app_state_machine_conformance.rs` builds the real artifact,
drives it through the bridge ABI with a thin Wasmtime client, and compares to the golden. A
mismatch names the first diverging `scenario / step / event index`.

```bash
cargo test -p traverse-runtime --test app_state_machine_conformance
# after an intentional runtime change, review the diff, then:
TRAVERSE_UPDATE_GOLDEN=1 cargo test -p traverse-runtime --test app_state_machine_conformance
```

The wasm32 build needs the pinned Rust 1.94.0 toolchain with the `wasm32-unknown-unknown`
target first on `PATH`.

## Known host differences

- **Swift rejected submits:** `WasmiHostBridgeClient.submit` throws on a rejected command, so the
  response body (`status: rejected`, `error`) is unavailable; the runner checks `guest_status`
  and the `error` event only for those steps.
- **.NET rejected submits:** `WasmtimeBridgeClient.Submit` throws `TraverseBridgeException`
  with the response JSON as its message; `RuntimeTraverseEmbedder.Submit(TraverseAppCommand)`
  maps that to a `rejected` result (with `Error`), matching web.
- **Web host status codes:** `RuntimeWasmHost.submit` throws on a rejected command and reports only
  "non-zero"; the runner records `guest_status: -1` and reads the response body from the error
  message.
- **Web public level:** `BundleEmbedder.ensureAppHost` requires at least one bundled wasm
  component even for a machine that only uses host connectors (it throws `state_machine invoke
  capability is not present in the bundle`), so a host-connector-only app cannot yet be driven
  through the public web API. The web runner therefore checks the bridge level only. The checked-in
  `tests/fixtures/runtime.wasm` also predates the app state machine, so the runner needs the
  generated artifact.
- **Public API scope:** raw terminal injection (duplicate terminal, late deadline) and rejected
  submits cannot be expressed through adapters and the timer port, so they are checked at the
  bridge level only.
